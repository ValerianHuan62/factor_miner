# V0.3 市场状态金融流程说明

## 先看金融过程

V0.3 不预测某只股票，也不直接产生买卖信号。它每天根据当时已经可见的全市场信息，估计市场更像哪一种统计环境，并输出每种环境的概率。这个“市场状态日历”以后用于回答：

- 某个因子的 RankIC 是否只在部分市场环境中有效；
- 相同因子在高波动、低流动性或市场宽度分化时，收益、回撤、换手和成本是否不同；
- 因子库在哪些环境中覆盖不足。

输入只有四个 point-in-time 市场特征：

1. 全市场中位数或等权日收益，描述市场整体方向；
2. 二十日实现波动率，描述价格风险；
3. 全市场成交额相对二十日均值的对数，描述流动性冷热；
4. 上涨股票占比，描述市场宽度。

股票池按当日状态决定，不能使用今天仍上市的股票去回填历史。ST、新股、停牌和无有效价格的股票不进入当日聚合；交易受限比例会单独保留为诊断。

## 研究期与正式期

研究期比较 `K=2、3、4`、两种收益聚合、三种训练窗口和两种 covariance。BIC 只是候选指标，正式排序优先看样本外对数似然、月度成功率、跨月映射稳定性和状态区分度。中位数收益与等权收益分轨比较，因为两个轨道的 likelihood 不可直接横比。

人工审阅研究报告后，只批准一个固定配置。正式期保持：

```text
K 固定
收益聚合固定
训练窗口固定
covariance 固定
拟合参数每月只用历史数据重估
```

因此正式运行不会因为某个月结果不好而临时改成另一个状态数。若当月拟合、正定性、状态占比、持续时间或冗余检查失败，该月明确输出 `unavailable`，不回退其他 K，也不沿用上月概率。

## 为什么波动不同不能随便合并

两个状态即使平均收益相近，只要波动率、下行风险、市场宽度、流动性或下游策略表现明显不同，就可能具有完全不同的交易含义。V0.3 只有在发射分布、占比、持续时间和转移行为等多个维度都接近时，才把状态冗余作为硬拒绝条件。

跨月状态编号使用完整距离矩阵和 Hungarian 全局匹配。系统同时保存 HMM 原始编号和跨月 canonical 编号；canonical 编号用于连续分析，但不被永久命名为“牛市”或“熊市”。

当前冻结正式快照在展示层使用两个人工中文经济标签：

- `高波动下跌·弱宽度`（`canonical_state_id=0`）；
- `低波动平稳·宽度中性`（`canonical_state_id=1`）。

数字 ID 只作机器审计键。中文名称来自当前快照的收益、波动、流动性和宽度聚合诊断，不是 HMM 自动发现的永恒市场类别；新快照必须重新审阅，不能自动继承旧名称。

中位数收益轨道选择两个状态，也不是因为 BIC 单独裁决。冻结排序优先看走步式样本外对数似然、月度成功率、跨月稳定性和经济区分度，BIC 只作辅助。部分三个状态候选虽然 BIC 更低，但样本外表现和稳定性更差；等权收益轨道最终仍选择三个状态，说明 `K` 是每条输入轨道完整验证后的结果。

## filtered probability 如何使用

日期 `t` 的输出只计算：

\[
P(S_t\mid X_1,\ldots,X_t)
\]

这是 filtered probability，不是使用未来观察的 smoothed probability。若在 `t` 日收盘后取得四个特征，状态最早只能在下一交易日使用。正式日表因此同时保存：

```text
observation_date
earliest_use_date
canonical_state_probabilities
max_probability
normalized_entropy
```

概率向量比单一标签保留更多不确定性。`max_probability` 高或熵低，只表示模型当时更偏向某个统计组件，不表示模型一定正确。

## 它能说明什么，不能说明什么

市场状态日历可以描述历史市场环境，并检验因子、组合和成本在不同环境下是否有差异。它不能证明某个状态具有因果含义，也不能证明一个因子有效，更不能直接决定仓位。

HMM 还可能用多个 Gaussian 近似同一个厚尾分布。一个模型只有在不同状态下能明显区分 RankIC、因子收益、回撤或换手成本时，才值得被下游使用。否则即使状态图看起来清晰，也只是研究诊断。

## 四条正式命令

研究阶段在公司 Linux 服务器执行：

```bash
factor-miner regime research regime_research_spec.json --env-file server.env
```

命令只读取行情与状态输入，不读取标签；它登记研究 Spec，并输出研究 ID、分轨推荐和研究报告路径。

人工选定候选后登记固定部署：

```bash
factor-miner regime register-deployment regime_deployment_spec.json \
  --report-path /data/factor_miner_artifacts/artifacts/regime_research/<研究ID>/regime_research_report.json \
  --artifact-root /data/factor_miner_artifacts
```

正式构建 filtered 状态快照：

```bash
factor-miner regime build \
  --deployment-id <部署ID> \
  --start 2010-01-01 \
  --end 2026-07-29 \
  --env-file server.env
```

`start` 必须覆盖所选训练窗口所需的历史。只读核验快照：

```bash
factor-miner regime verify /data/factor_miner_artifacts/artifacts/regimes/<快照ID>
```

快照固定保存部署合同、月度模型、filtered 日表、市场特征、质量诊断、人工注释和 manifest。全部文件都进入 SHA-256 内容身份；任何字节变化都会被发现。真实数据、模型和完整结果不进入 Git。

## V0.4 与 V0.5 如何使用

V0.4 将构建现有因子覆盖图谱：

- 数学形式维度：字段、算子、窗口、AST 和因子分类；
- 实际信号维度：逐日截面 Spearman IC 时间序列，以及因子两两相关结构；
- 环境维度：各因子在 V0.3 不同状态概率下的 IC、稳定性、换手和成本特征。

逐日 IC 相关矩阵必须按因子对逐一对齐、逐一计算，不能先把缺失模式不同的序列直接拼成统一向量后批量相关。

V0.5 才接入 LLM。LLM 读取经过压缩和脱敏的覆盖图谱，寻找因子库欠缺方向，提出金融假设和受限 DSL 候选。它不能读取公司原始数据、个股样本、完整结果、账本、模型或密钥，也不能执行任意 Python。每个候选仍必须经过预登记、无前视校验、HAC、Bonferroni、冗余和残差增量信息协议。

因此，完成 V0.5 后可以开始由 LLM 辅助挖因子，但输出仍只能称为“通过可见增量信息验证的候选因子”。CPCV、Deflated Sharpe Ratio、交易成本、组合检验和密封样本外认证属于更后阶段。
