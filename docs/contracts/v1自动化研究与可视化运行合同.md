# V1 自动化研究与可视化运行合同

## 研究边界

本合同的输出只能称为“通过冻结可见协议计算的候选因子诊断”。它不是有效 Alpha、
生产因子或因果机制证明。生成前冻结假设、字段可用性、评价政策、组合政策、数据
身份和 120 槽统计预算；结果产生后不能补抽、改参数或缩小多重检验分母。

所有真实候选计算、IC、组合回测和 Barra 归因只在公司 Linux 执行。Mac 只能运行
合成测试、查看哈希和通过 SSH 隧道访问 Dashboard。QuantLake 是只读上游，原始行情、
逐股票面板、完整失败账本、密钥和模型请求/响应正文不得进入 Git、Mac 或外部模型。

## 固定研究族

V1 沿用四条 arm、总计 120 个候选槽：

```text
coverage_outcome_llm       30 槽 = 10 个假设 × 3 个设计
literature_only_llm       30 槽 = 10 个假设 × 3 个设计
mechanical_mutation       30 槽 = 10 个假设 × 3 个设计
hypothesis_conditioned_grammar 30 槽 = 10 个假设 × 3 个设计
```

每次 LLM arm 最多处理 10 个经人工批准的假设。个人试运行不要求逐个批准请求哈希；
在服务器生成一次绑定研究族、角色、信息类别、假设数量、调用次数和有效期的
`LLMCampaignScopeAuthorization` 后，固定程序会对每一次实际请求重新执行脱敏扫描和
范围核验，并保存请求哈希。旧的精确请求授权仍可用于高风险或单次试验。
候选表达式只允许白名单 typed AST，字段、单位、可用时点、lookback、前视和重复检查
由固定程序决定。LLM 不接收 IC、收益、Sharpe、回撤或 Barra 结果。

## 服务器运行顺序

服务器私有目录需先准备以下文件：批准假设、公司外发政策、脱敏公共 payload、字段
可用性注册表和个人试运行范围授权。路径和密钥只从服务器私有环境读取，不写入命令输出。

```bash
uv sync --frozen --extra dashboard

factor-miner llm authorize-scope \
  "$FM_APPROVED_FAMILY_ID" \
  /data/factor_miner_artifacts/private_config/corporate_external_policy.local.json \
  --output /data/factor_miner_artifacts/private_config/v05_expression_scope_authorization.json

factor-miner llm prepare-approved \
  "$FM_APPROVED_FAMILY_ID" \
  /data/factor_miner_artifacts/private_config/v05_hypothesis_approved.json \
  /data/factor_miner_artifacts/private_config/corporate_external_policy.local.json \
  /data/factor_miner_artifacts/private_config/v05_expression_public_payload.json \
  --artifact-root /data/factor_miner_artifacts

factor-miner llm run-approved \
  "$FM_APPROVED_FAMILY_ID" \
  /data/factor_miner_artifacts/private_config/v05_hypothesis_approved.json \
  /data/factor_miner_artifacts/private_config/corporate_external_policy.local.json \
  /data/factor_miner_artifacts/private_config/v05_expression_public_payload.json \
  /data/factor_miner_artifacts/private_config/v05_field_registry.local.json \
  /data/factor_miner_artifacts/private_config/v05_expression_scope_authorization.json \
  --artifact-root /data/factor_miner_artifacts
```

中断时只使用 `resume-approved` 恢复已经写入的不可变请求、响应和候选对象；不能以
“重试”为理由生成新的研究想法。四条 arm 的全部 120 个槽必须有成功、失败、重复、
人工否决或基础设施终止等不可变终态后，才能运行：

coverage arm 的批准候选完成后，服务器固定程序运行两个不读取结果的确定性对照：

```bash
factor-miner llm shadow-run \
  "$FM_APPROVED_FAMILY_ID" \
  /data/factor_miner_artifacts/private_config/v05_coverage_hypothesis_approved.json \
  /data/factor_miner_artifacts/private_config/v05_field_registry.local.json \
  --artifact-root /data/factor_miner_artifacts
```

`shadow-run` 只复用同编号、已通过固定编译的 coverage 父候选；每个批准假设在
`mechanical_mutation` 与 `hypothesis_conditioned_grammar` 各占 3 个槽。未批准假设
和没有合格父候选的槽分别写入明确的未执行终态，不能借用别的假设或读取 outcome。

四条 arm 的全部 120 个槽必须有成功、失败、重复、
人工否决或基础设施终止等不可变终态后，才能运行：

```bash
factor-miner llm family-seal-auto \
  "$FM_APPROVED_FAMILY_ID" \
  /data/factor_miner_artifacts/private_config/v05_generation_seal_input.json \
  --artifact-root /data/factor_miner_artifacts
```

`family-seal-auto` 会从服务器本地槽对象重算 hash；调用者不能传入脱离实际对象的
hash。没有完整 seal 时，结果端口必须硬失败，不能读取组合、IC 或 Barra 输入。

## 金融计算合同

封存后，固定服务器 runner 读取版本化交易日历、状态表、开盘价、因子面板、沪深300
基准和 Barra 输入，执行以下口径：

- 每周二调仓；周二休市顺延到该周第一个开放日；信号使用前一实际交易日收盘；
  入场和退出均为开盘，收益为 open-to-open。
- 十个多头分组，组内等权；多空为 Q10−Q1 和 Q9−Q2；成本为冻结的双边 14bp。
- 保存毛收益、净收益、回测期收益、实际交易日日历年化收益、净 Sharpe、最大回撤、
  相对沪深300超额收益、信息比率和换手。
- 保存 IC/RankIC 均值、标准差、IR、HAC t 统计量、阈值概率、1/3/5/10/20 日衰减、
  分布、序列和自相关诊断。
- 保存 Barra 行业、Size/风格主动暴露及已实现因子贡献；缺少协方差或特异风险时，
  状态必须是 `realized_attribution_only`，不能伪造完整风险分解。

完整结果先写独立暂存目录，核验所有文件哈希后原子发布；最后才追加候选和运行终态。
失败候选也必须保留失败终态，不能因失败而删除统计槽位。

## 阶段 B：DeepSeek 假设到 Pilot

阶段 B 在正式 120 槽治理之前单独运行。它使用非 family 的
`pilotstage_<24位十六进制>` 身份，不读取、不修改、不追加旧的
`llmfamily_1bae19965638a6ac9620e0b0`。一条批准假设最多生成三个表达式，三个表达式共用
阶段 A 的因子计算、IC、组合、Barra 可选归因、产物发布和 PostgreSQL 投影协议。

服务器命令顺序固定为：

```bash
factor-miner pilot prepare-hypothesis <public_brief.json> \
  --artifact-root <pilot_stage_b_artifact_root> --output <hypothesis_request.json>
factor-miner llm authorize-export <hypothesis_request.json> <policy.json> \
  --approved-request-sha256 <request_hash> --approver-role <role> \
  --output <hypothesis_authorization.json>
factor-miner pilot generate-hypothesis <hypothesis_request.json> <policy.json> \
  <hypothesis_authorization.json> --artifact-root <pilot_stage_b_artifact_root> \
  --record-root <private_call_root> --output <hypothesis_response.json>
factor-miner pilot approve-hypothesis <hypothesis_response.json> \
  --artifact-root <pilot_stage_b_artifact_root> --output <approved_hypothesis.json> \
  --approver-role <role>
factor-miner pilot prepare-expression <approved_hypothesis.json> <field_registry.json> \
  --artifact-root <pilot_stage_b_artifact_root> --output <expression_request.json>
factor-miner pilot run-approved <expression_request.json> <approved_hypothesis.json> \
  <policy.json> <expression_authorization.json> <field_registry.json> <pilot_config.json> \
  --artifact-root <pilot_stage_b_artifact_root> --record-root <private_call_root> \
  --dsn <optional_dashboard_dsn>
```

`generate-hypothesis` 和 `run-approved` 只允许在公司 Linux 执行。外发请求只包含公开
简报、已核验来源标识、字段能力、允许算子和输出 Schema；不得包含行情、个股、标签、IC、
收益、Sharpe、回撤、Barra 或服务器路径。人工批准记录绑定假设内容哈希；表达式响应先
经过本地 Schema、字段白名单、lookback、可得性、未来函数和确定性 compiler 硬校验，任何
失败都不得进入阶段 A。semantic lint 只作为非阻塞诊断保存，不能改写 AST。

阶段 B 的可视化使用独立操作台 `dashboard/stage_b_console.py`，只读结果 Dashboard 不
增加批准或重新回测按钮。操作台通过正式 CLI 发起动作，展示阶段状态、批准身份、请求和
响应哈希以及最终 `pilot_run_id`；数据库仍只是可重建读模型。

## 阶段 C：120 槽正式研究族治理

阶段 C 恢复正式研究族的不可变事件账本、四条 arm、120 个预登记槽、generation seal、
统一评价器和 Dashboard 发布。阶段 A、阶段 B 的 Pilot 产物不自动升级为正式研究族；
正式研究族必须使用新的 `family_id`，不能复用或修补污染的
`llmfamily_1bae19965638a6ac9620e0b0`。

生成阶段只允许追加通过状态机校验的事件。校验在单写入器锁内完成，非法状态转换、重复
对象、哈希链损坏和已知污染族均硬失败；失败事件不能通过覆盖或删除修复。未获批准假设、
表达式校验失败和基础设施中断都必须占用原槽并写入明确终态。恢复只能继续未完成槽，不能
重抽假设或缩小 120 的统计分母。

只有 120 个槽都进入终态，且槽对象哈希、数据身份、评价关系、评价政策和统计预算一致，
固定程序才能生成不可逆 `generation_seal`。seal 核验之前，评价器不得读取标签、IC、收益、
组合、冗余或 Barra 结果。seal 之后任何槽位替换、状态逆转、事件篡改或对象哈希变化都会
导致核验失败；纠错必须新建研究族。

seal 后统一评价器对全部 120 个槽保留结果记录：成功槽使用冻结的 HAC 参数，RankIC
显著性使用 Bonferroni 分母 120；失败、未执行和高冗余槽仍留在分母中。规范 AST 重复和
可见区间逐日截面 Spearman 高相关候选保留审计记录但不通过。发布清单同时绑定
`family_id`、`generation_seal_id`、评价政策哈希、数据合同身份哈希和统计预算哈希，
Dashboard 只读取发布后的只读投影。

阶段 C 的服务器入口为：

```bash
factor-miner campaign run-approved <new_family_id> \
  <approved_hypotheses.json> <policy.json> <payloads.json> \
  <field_registry.json> <authorizations.json> \
  --artifact-root <stage_c_artifact_root>

factor-miner campaign seal <new_family_id> <seal_input.json> \
  --artifact-root <stage_c_artifact_root>

factor-miner campaign evaluate <new_family_id> <evaluation_results.json> \
  --artifact-root <stage_c_artifact_root> --dsn <dashboard_dsn>

factor-miner campaign verify <new_family_id> \
  --artifact-root <stage_c_artifact_root>
```

`campaign evaluate` 的输入必须来自服务器统一 Pilot 评价器，按 `slot_id` 提供全部槽位；
命令不接受跳过 seal、缩小预算、替换策略或隐藏失败槽的选项。PostgreSQL 只保存可重建的
Dashboard 读模型，正式 JSON/JSONL 产物和事件账本仍在独立服务器产物根目录。

## V0.6 记忆辅助演化 CLI 合同

V0.6 在既有阶段 A、B、C 约束之上增加人工闸门，不改变 120 槽、HAC、Bonferroni、typed AST、未来信息防火墙、服务器数据边界或 seal 规则。正式入口为：

```text
factor-miner evolution prepare-context --coverage-graph-root <verified-root> --memory-root <formal-root> --memory-snapshot-id <snapshot-id> --gap-report <formal-gap-report.json> --family-id <new-family> --policy <frozen-policy.json> --output <context.json>
factor-miner evolution generate-hypotheses --context <context.json> --authorization <request-authorization.json> --output <draft-batch.json>
factor-miner evolution approve-hypotheses --context <context.json> --draft-batch <draft-batch.json> --decisions <human-decisions.json> --output <approved-batch.json>
factor-miner campaign run-approved --evolution-context <context.json> --approved-hypotheses <approved-batch.json> ...既有冻结 Stage-C 参数...
```

`prepare-context` 必须调用现有 verified graph loader/validator，读取正式 memory index 指定的 snapshot 和显式 gap report；必须绑定 graph manifest、snapshot 内容 hash、snapshot 的 graph manifest hash、gap report 的 graph/memory hash、cutoff 前已完成 entry、field registry hash、evaluation policy hash 和 design policy hash。禁止只用 glob 或任意 JSON 猜测身份。`generate-hypotheses` 至少保存 `request_sha256`、`response_digest`、`provider`、`model` 和脱敏 `prompt_bundle`，禁止保存原始模型响应，并生成绑定十个 `draft_sha256` 的 `draft_batch_sha256`。`approve-hypotheses` 是唯一批准入口，必须从 draft JSON 原样核对 `request_sha256`、`report_sha256`、`gap_card_sha256`、`context_sha256`、`discovery_family_id`、十个 draft hash 和 `draft_batch_sha256`；不得用当前 context 或 decisions 重建这些字段。随后逐条核对十个 decision hash、审批角色；批准批次必须正好覆盖 H01-H10，并逐条绑定 `context_sha256`、`draft_sha256`、`discovery_family_id`、审批角色、时区时间和 `decision_sha256`。`campaign run-approved` 必须再次核对同一 draft batch provenance 和 `approval_batch_sha256`，任何负例均须在表达式、回测或发布前失败且不产生 output。

不变量包括：family、context、graph、memory、gap 和批准批次 hash 一致；污染 family 硬失败；数量不是十、审批不足十个或设计预算不是 10/3/4/120 时非零退出；批准校验失败发生在创建表达式请求、回测任务和发布产物之前。失败、重复、`DESIGN_DIVERSITY_FAILED`、`cross_arm_redundant` 与 `not_executed` 均保留槽位和纠正事件，不能从分母消失。seal 必须重新核验上述身份链，Dashboard 只读取发布后的脱敏投影。
