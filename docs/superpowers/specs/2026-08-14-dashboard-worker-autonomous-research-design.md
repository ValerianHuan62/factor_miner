# Dashboard 与单机 Worker 自主研究设计

## 1. 目标与研究边界

本设计把 Factor Miner 从“用户通知 Codex，再由 Codex 调用 DeepSeek 和服务器命令”改为服务器自主运行。用户日常只需要在 Dashboard 中启动批次、审阅十条假设并冻结运行；Codex 不再参与正常研究链路，只用于后续开发和故障排查。

自动化不得改变金融研究边界：候选在读取任何标签、IC、收益、Sharpe、回撤或输出相关性前完成假设审批、表达式校验、候选登记和统计检验族冻结。系统输出仍只能称为“通过可信可见验证的候选因子”，不能称为认证因子、有效 Alpha 或生产结论。

分钟聚合字段在当日收盘后才完整可得，最早在下一交易日开盘使用。原始行情、个股样本、完整结果、账本、模型和密钥不得发送给 DeepSeek。

## 2. 已确认的产品决策

- 使用 Dashboard 与单机研究 Worker，不引入 Celery、Redis 或定时任务。
- Dashboard 提供“新建研究批次”按钮，用户可以不定时、高频启动研究。
- 同一时间只允许一个活动批次；重复命令根据内容哈希幂等去重。
- DeepSeek 一次生成固定十条中文假设。
- Dashboard 完整展示十条假设，用户必须逐条选择“批准”或“拒绝”。
- 十条决策全部完成前不得冻结和运行。
- 拒绝的假设不补抽、不生成表达式，但必须进入下一轮研究记忆。
- 所有已批准假设合并为一次 DeepSeek 表达式请求，每条假设固定生成三个 AST。
- 正常批次只调用 DeepSeek 两次；Codex 不参与日常运行。
- Dashboard 不展示 TOKEN 数，只展示研究状态、进度、候选数量和错误。
- 采用深色研究指挥舱视觉，以及“左侧目录、中间完整正文、右侧决策”的主从审批布局。

## 3. 方案选择

### 3.1 未采用：Dashboard 直接执行完整 CLI

这种方式改动少，但 Streamlit 请求会被长任务占用，页面刷新、浏览器关闭或服务重启容易中断运行，也难以清晰恢复到具体阶段。

### 3.2 采用：Dashboard 与单机研究 Worker

Dashboard 只提交控制命令并读取状态；Worker 是研究状态、文件账本和运行产物的唯一写入者。关闭浏览器不会中止研究，Worker 重启后能够核验已有不可变阶段文件并从下一阶段继续。

### 3.3 未采用：Celery 与 Redis

当前项目只需要单机、单活动批次和单写入器。引入分布式任务系统会增加运行服务、状态一致性和部署成本，不符合个人项目的简化目标。

## 4. 总体架构

系统由五个边界清晰的组件组成：

1. `Research Control Dashboard`：提交新建批次、审批决定、冻结运行和继续执行命令；展示已校验的中文假设和运行状态。
2. `Research Command Inbox`：保存内容寻址的原子命令文件。Dashboard 只写命令，不直接写研究状态或正式账本。
3. `Factor Miner Worker`：轮询命令收件箱，调用轻量研究协调器并维护单活动批次租约；它是研究状态的唯一写入者。
4. `Deterministic Research Pipeline`：复用现有字段注册、白名单 AST、compiler、真实数据端口、IC/HAC、组合评价、发布器和 PostgreSQL 投影，不重新实现金融计算。
5. `DeepSeek Provider`：只接收脱敏上下文、公开字段能力、冻结 Schema 和批准假设；不读取任何研究结果。

Worker 以 Linux `systemd` 服务运行，服务名固定为 `factor-miner-worker.service`。不新增 cron。Dashboard 和 Worker 均在现有服务器边界内运行。

## 5. 状态机与数据流

轻量研究阶段固定为：

1. `准备上下文`
2. `生成假设`
3. `等待审批`
4. `审批已冻结`
5. `生成表达式`
6. `候选已登记`
7. `计算与评价`
8. `产物已发布`
9. `数据库已投影`
10. `记忆与图谱已刷新`
11. `完成`

完整数据流如下：

```text
Dashboard 新建研究批次
  → Worker 读取上一轮记忆、覆盖图谱和字段能力
  → 构造并冻结脱敏研究简报
  → DeepSeek 一次生成十条假设
  → Schema 校验并保存不可变假设批次
  → Dashboard 等待十条逐项批准或拒绝
  → Worker 冻结完整审批集合
  → DeepSeek 一次批量生成所有批准假设的三个 AST
  → 本地执行字段、时点、lookback、结构和未来函数校验
  → 登记候选并冻结 manifest 与统计检验族
  → 在公司 Linux 使用真实数据计算和评价
  → 发布完整候选包
  → 投影 PostgreSQL 中文读模型
  → 追加本批全部假设和候选终态到研究记忆
  → 更新因子覆盖图谱和下一轮缺口简报
  → 完成
```

审批发生在表达式生成、候选登记和结果读取之前。统计检验族在审批完成且表达式槽位确定后、读取任何结果之前冻结为 `批准假设数 × 3`。例如批准七条假设，则冻结二十一个候选槽；之后的表达式失败、编译失败、数据不可用和计算失败仍留在这二十一个槽中，不补抽、不缩小 Bonferroni 分母。

若十条假设全部拒绝，批次以“无批准假设”终态结束，十条拒绝记录进入研究记忆，不调用表达式模型，也不创建空评价批次。

## 6. Dashboard 交互设计

### 6.1 批次控制

- 顶部显示 Worker 在线状态、当前批次、当前阶段、开始时间和最近错误。
- 空闲时显示“新建研究批次”。存在活动批次时不允许创建第二批。
- 阶段失败时显示“从当前阶段继续”；继续命令不能回退或重复已完成阶段。
- 页面关闭或刷新不影响 Worker。

### 6.2 假设审批工作台

采用已确认的深色主从布局：

- 左侧显示 H01 至 H10 的目录、短标题和 `待审阅/已批准/已拒绝` 状态。
- 中间显示当前假设的完整正文并允许页面滚动，禁止截断和省略号。
- 完整正文至少包含主张、机制、预期方向、可观察代理、独立验证、竞争解释、失效方式、证伪路径、来源和机制验证状态。
- 右侧显示审批进度、信号可得时点以及批准和拒绝按钮。
- 摘要目录不能直接审批。审批决定只在完整正文视图提交。
- 整批冻结前允许修改尚未冻结的决定；冻结后所有决定不可修改。
- 每个决定绑定假设全文哈希、批次身份、审批角色和带时区时间。

### 6.3 运行状态

Dashboard 不展示模型 TOKEN 数。运行中展示中文阶段名称、已完成步骤、当前候选数、失败槽位数和最近错误。研究结果只从 PostgreSQL 完整读模型加载；不完整指标不得显示为零。

视觉风格采用深蓝黑背景、青绿色成功状态、低饱和红色拒绝状态和蓝色信息状态。参考成熟研究终端的视觉层级、密度与间距，但不复制第三方网站源码、品牌或受版权约束的视觉资产。

## 7. 模型调用与成本控制

正常批次最多包含两次 DeepSeek 调用：

1. 一次生成十条假设。
2. 一次为全部批准假设批量生成表达式。

默认不调用额外的 LLM semantic lint。表达式语法、字段存在性、可得时点、lookback、白名单算子、节点深度、结构差异和未来函数由本地确定性代码检查。

DeepSeek 上下文不包含完整历史记忆。Worker 只发送聚合失败模式、有效结构摘要、覆盖缺口、公开字段能力、最近三批摘要和最多十张缺口卡片。固定提示模板和输出 Schema 单独版本化；请求身份绑定批次、上下文哈希、审批集合和提示版本。

已存在合法录制响应时，重启 Worker、重复命令或继续执行只能读取已有响应，不能再次调用模型。

## 8. 重试与失败语义

- 网络在尚未收到响应前中断时，Worker 自动重试一次。
- 响应整体格式错误时，允许一次只修格式的精简请求。
- 仅部分批准假设的 AST 无效时，修复请求只包含失败项，不重发完整批准集合。
- 修复后仍失败的槽位记录为失败，不补抽；其他候选继续。
- 因子计算、评价或发布失败时不再调用 DeepSeek，从对应阶段恢复。
- 正式产物发布成功但 PostgreSQL 投影失败时，只重试投影，不回滚发布。
- 记忆或图谱刷新失败时，已发布研究结果不回滚，只重试进化刷新。
- 失败信息必须是中文、可审计且不包含密钥、原始行情或 DeepSeek 原始响应。

格式修复调用和失败子集修复属于异常路径，因此真实故障批次可能超过两次 DeepSeek 调用；正常批次保持两次。

## 9. 存储与数据库边界

JSON、JSONL 和不可变候选包继续作为正式主存储。命令、阶段状态、审批集合、请求、响应摘要、manifest、发布引用和进化引用全部内容寻址。PostgreSQL 只作为 Dashboard 读模型，不成为文件账本失败时的兜底。

PostgreSQL 字段名保持英文；假设内容、阶段名称、失败原因、因子解释和其他描述性文本使用中文。因子业务编号继续由数据库事务串行分配稳定的 `huanNNN`；同一 `source_candidate_id` 永久复用同一编号。

DeepSeek 原始响应和服务器私有路径不进入 PostgreSQL。Dashboard 只展示通过固定 Schema 校验后的中文假设。Stage C 已评价候选仍必须具备完整 IC、RankIC、HAC、IR、胜率、收益、回撤、Sharpe 和 information ratio 才能发布与投影。

## 10. 记忆与因子图谱

轻量批次使用独立适配层写入现有研究记忆和因子图谱，不直接放宽旧 120 槽、四臂和 generation seal 合同。

本批十条假设的批准、拒绝和失败终态都进入记忆。批准假设下的三个候选还记录规范 AST、字段签名、时间结构、评价摘要、失败原因和冗余关系。分钟聚合候选在图谱中使用明确的 `intraday_aggregate` 数据来源标签。

当前批次只能读取启动时冻结的旧记忆和旧图谱。本批新记忆和新图谱只供下一批读取，禁止同批自我反馈。只有新记忆快照、覆盖图谱和中文缺口简报三者身份均可核验时，运行才进入“记忆与图谱已刷新”。

## 11. 测试与部署验收

### 11.1 Mac 合成测试

使用程序生成的纯合成输入测试：

- 命令收件箱的原子性、幂等性和单活动批次；
- 十条假设完整 Schema 和逐条审批；
- 未完成十条决策时禁止冻结；
- 全部拒绝时不调用表达式模型；
- 批量表达式请求只调用一次；
- 部分格式失败只修复失败子集；
- 动态检验族分母等于批准假设数乘三；
- 阶段恢复不重复调用模型或发布器；
- Dashboard 完整正文不截断，摘要区不能审批；
- 中文状态和错误投影；
- 当前批次不读取本批新记忆。

Mac 测试不得读取或复制公司真实行情、个股样本和研究结果。

### 11.2 Linux 录制响应验收

在公司服务器使用已录制、无真实行情内容的 DeepSeek 响应运行完整 Worker 流程，验证服务重启、命令重放、候选登记、真实评价端口接线、PostgreSQL 中文投影、记忆和图谱刷新。该阶段不得产生新的模型费用。

### 11.3 Linux 真实验收

部署 `factor-miner-worker.service` 和新版 Dashboard 后不自动调用模型。第一次真实调用只能由用户点击“新建研究批次”触发。用户完成十条审批并点击冻结运行后，即使浏览器关闭，Worker 也必须继续至完成或可恢复失败状态。

最终验收路径是：打开 Dashboard → 新建批次 → 审批十条假设 → 冻结并运行 → 查看状态变为完成。正常路径不需要 Codex、终端命令或第二个人工授权页面。

## 12. 不在本次范围内

- 多用户与复杂权限系统；
- 多活动批次并发；
- Redis、Celery、Kubernetes 或分布式 Worker；
- 定时或数据更新自动触发；
- Dashboard 在线修改 DeepSeek 假设正文；
- 用 LLM 读取评价结果后自动解释或选择候选；
- 自动晋级生产因子或策略实盘；
- 放宽前视、冻结、完整指标、多重检验和数据外发边界。
